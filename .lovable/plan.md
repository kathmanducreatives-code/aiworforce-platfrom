# Fix: qualified-Lead requests routed into legacy fast/account_first

## Confirmed root cause (traced, not guessed)

Both intent modules already classify the canonical query correctly:

- `routeQualifiedLead("Find 5 founders or CEOs …")` → `workflowKind: qualified_lead_sourcing`, `executionMode: company_first`, `countEntity: contact_ready_lead`, `quotaPolicy: contact_only`.
- `compileLeadEntityIntent(...)` → `target_entity: person`, `execution_mode: company_first`, `company_gate_required: true`.

The defect is **structural, at two seams** where those outputs are not consulted:

1. **`supabase/functions/pilot-chat/index.ts:1968-1996`** — the `company_hiring_sourcing` branch of the workflow classifier hardcodes `tool_input = { selected_actor_key: "apify_jobs", source_type: "jobs", execution_mode: "fast", … }` without ever calling `routeQualifiedLead`. That `tool_input` is forwarded verbatim through orchestrate (`delegateToOrchestrate`, `pilot-chat/index.ts:583-587`) to run-agent.
2. **`supabase/functions/run-agent/index.ts:637-638`** — the gate that runs `compileLeadEntityIntent`/`isCompanyFirstRequest` is `if (!raw_source_type && !planned_actor_key)`. Because pilot-chat already pinned `source_type="jobs"` and `selected_actor_key="apify_jobs"`, this block is skipped, `routingEntityIntent` stays `null`, and the company-first branch at line 686 is never entered. `body.workflow_kind` / `body.execution_mode` (which orchestrate correctly stamps at `orchestrate/index.ts:1222-1235`) are **not read as an entry condition** — only inside the already-entered branch (line 893).

Execution then falls to the legacy account path, where `leadIntentModel.ts:90` unconditionally defaults `source_strategy: "account_first"` for any non-named-company request.

**"Found 2 of 5"** is generated by `run-agent/index.ts:3374-3383` (`partialPrefix = "Found ${produced} of ${requested}. "`) — a backend chat message from legacy `sourceQuality` counters. The correct UI renderer (`buildQuotaProgress` via `LeadResultsView.tsx:145-155`) is gated on `meta.qualified_lead_run.count_entity === 'contact_ready_lead'`, which is never populated because the company-first branch never runs. Once seam #1 is fixed, this text is unreachable for this class of request.

## Scope

Single PR, backend-only routing fix plus regression tests. No UI change required for the reported defect. No deploys, no migrations, no flag changes, no live provider/model calls. Intelligence flags remain OFF; the fix does not depend on them.

## Changes

### 1. `supabase/functions/pilot-chat/index.ts` (~lines 1960-1996, `company_hiring_sourcing` branch)

Before building `toolInput`, evaluate `routeQualifiedLead(message)`. When it returns `workflowKind === "qualified_lead_sourcing"`:

- Omit `selected_actor_key` and `source_type` from `toolInput` (leave them undefined/null so run-agent's existing `!raw_source_type && !planned_actor_key` gate fires).
- Thread `workflow_kind`, `execution_mode: "company_first"`, `quota_policy`, `count_entity`, `requested_lead_count` on the delegation payload — mirroring what `orchestrate/index.ts:1222-1235` already does downstream.

Non-qualified `company_hiring_sourcing` requests (e.g. "Show companies hiring Sales Operations") keep the current `apify_jobs` behavior.

### 2. `supabase/functions/run-agent/index.ts` (line 637-638 gate, defense-in-depth)

Widen the entry condition so an explicit body contract short-circuits a pre-pinned `tool_input`:

```
if (
  body.workflow_kind === "qualified_lead_sourcing" ||
  body.execution_mode === "company_first" ||
  (!raw_source_type && !planned_actor_key)
) { /* compileLeadEntityIntent … */ }
```

This closes the seam even if a future caller pins an actor while declaring a qualified-lead contract. Direct lead actions (`isDirectLeadActionAttempt`, line 170) and `resume_task_id` continuations (line 163) never carry `workflow_kind`, so they are unaffected.

## Backward compatibility & risks

- **Direct lead actions**: no `workflow_kind` on body → unchanged.

- **Non-qualified `company_hiring_sourcing`**: `routeQualifiedLead` returns `account_opportunity_sourcing` → pilot-chat still pins `apify_jobs` → unchanged.
- **`people_sourcing` category** (`pilot-chat/index.ts:2002`): out of scope; noted as a follow-up audit — its `selected_actor_key` default has the same pinning pattern but the canonical query does not route there.
