- **Base:** R1.1 (`pilot-chat` at `a1633f45`, live).

## 1. Findings and root causes

| # | Finding | Verdict | Root cause (exact) |
|---|---|---|---|
| 1 | Executive brief labelled as a LinkedIn and campaign draft (15:11:34); the internal management report routed correctly (08:11:32) | **Defect** | `draftKindsFor` matched format words inside a negation: "…an internal analysis report, **not a LinkedIn post, email, marketing draft or campaign**". Because draft kinds were present, `isInternalAnalysis` was false and every compose request drafted. The 08:11 report named no formats, so it worked. |
| 2 | An Apify plus LinkedIn execution request was refused, but got a "LinkedIn message" Draft Only chip (08:14:00) | **Defect** | The draft check ran **before** the "do not execute" check, and "**send** each founder a LinkedIn message" matched the `linkedin_message` format. The model then refused correctly, but `metadata.orion_draft` was already set, so the chip showed. |
| 3 | ORION sees totals for 37 signals but no row-level signals | **Defect** | `retrieveEvidence` ranks all evidence and then cuts at **50 across sources**. Production's 61 leads are "agent inference" (rank 2); all 37 signals are "unverified" (rank 3: no verification level, status `unverified`). So the top 50 were all leads and **zero signals ever reached ORION**: every evidence panel in the session was 8 leads. Separately, no bounded row-level signal listing existed. |
| 4 | A compound follow-up answered partly or not at all (15:26:26) | **Defect** | `orionRoute` sent any read with a back-reference ("these companies") to the scoped list template ("Those 8: …"), even when it asked for judgement. Neither question was answered. |
| 4b | "Second company you just selected" was blocked (15:19:58) | **Correct behaviour** | ORION's previous answer said the three companies were tied ("None can defensibly be selected"). Asking which one is right. |
| 4c | Follow-up referents | **Latent defect** | Referents were the 8 default `[E#]` lead subjects, not the companies the answer discussed. "The second one" would have meant Newton Software. |
| 5 | Eight ATLAS leads attached to a Company Brain audit and to own-company content | **Defect** | `selectEvidenceForQuestion` always filled up to 8 items from the pool. A topic signal named "buyer-intent" also matched "buyer roles" through first-word matching. |
| 6 | Dates | **Defect (labels)** | A lead's `created_at` (when ATLAS saved it) was presented alongside hiring claims, and the model called it "observed". A signal with no event date was dated by its observation, implying an age. Ages counted elapsed 24-hour periods, not calendar days. |
| — | Data limitations, not defects | **Incomplete data** | In production: 35 of 37 signals have no event date; the 21 hiring and 2 funding signals have no source URL; 14 market and competitor signals are topics, not companies; no signal carries a verification level. R1.2 reports these fields as "not recorded" / "not stored". |

## 2b. Safety audit: unattended monitoring and legacy conversations (read-only, 2026-11-16)

### Production monitoring scan (Apify attempts on 2026-11-14 and 2026-11-15)

| Question | Finding |
|---|---|
| **Scheduler** | `pg_cron` job 1 `monitoring-tick`, `*/15 * * * *`, active. It POSTs `run-monitoring-tick` with the service-role bearer. |
| **Authorization path** | `run-monitoring-tick` v31 (deployed 2026-08-25) accepts only the service-role token (401 otherwise). It calls `run-monitoring-scan` v111 (deployed 2026-10-11) with the service role, which skips the membership check meant for people. |
| **What it selected** | The one subject with `enabled = true`: `78372f06…` (competitor, cadence 1,440 min) in workspace `11111111-…-5555`. That workspace has **0 members**: an orphaned demo workspace. It is scanned daily. |
| **Execution guards** | (1) subject `enabled`; (2) cadence; (3) period ceiling (`monitoring_budgets`: 200 credits per 7 days; spent 0); (4) per-call credit reservation (`[credits][authorization] mode: enforce … reserved`). **There is no feature flag.** `AGENTORY_DELEGATION_ENABLED=false` does not apply to monitoring. |
| **Why nothing was spent** | Production has an Apify token configured (`apify_token: true` in pilot-chat's startup log), and Apify **rejects** it (`apify_unauthorized`, 0 cost units). |
| **Can paid monitoring start when "the feature is disabled"?** | **Yes, if the Apify token becomes valid.** Nothing but the subject flag and the credit ceiling stops a scheduled paid scan. This is a **confirmed gap**, outside R1.x code. |
| **Other paid paths** | 48 h of function logs show no other Apify, LeadOcean or Firecrawl activity. `resume-stalled-leads` (every 3 minutes) had nothing to resume (0 queue rows). ORION never starts paid work (delegation off; R1.2 tests). |

**Containment (needs approval; prepared, not run):** `scripts/release/r12-monitoring-containment.sql`.
- **Option A, recommended:** disable the one enabled subject. One row, reversible.
- **Option B:** pause cron job 1.
- **Option C:** set that workspace's ceiling to 0.

**Durable fix (R2):** require `AGENTORY_MONITORING_ENABLED=true`, and refuse workspaces with no members.

### Conversations with no `workspace_id`

| Question | Finding |
|---|---|
| **Data** | All 126 production conversations have `workspace_id` NULL and one owner (`user_id` NOT NULL). There is one user. |
| **Ownership enforcement** | RLS on `conversations`: select, insert, update and delete only where `user_id = auth.uid()`. On `messages`: only through an owned conversation; no client UPDATE policy. `anon` has table grants, but RLS returns nothing without `auth.uid()`. `pilot-chat` (service role) checks `existing.user_id === userId` and returns 404 otherwise. |
| **Cross-user exposure** | **None found.** Every path checks the owner. |
| **Cross-workspace exposure** | A **latent gap**. `pilot-chat` created conversations without `workspace_id`, so one user in two workspaces could reuse a conversation (and its earlier turns) across workspaces. Data reads stay workspace-scoped, so only text that user already saw could carry over. Not exploitable across users, and not reachable today (one user, one member). |
| **Fixed in R1.2** | New conversations are stamped with `workspace_id`. Reusing a stamped conversation in another workspace returns 404. Legacy NULL rows keep working and are not rewritten. The column already exists (nullable, foreign key to `workspaces`) in production, TEST and the baseline. **No migration.** |

## 8. Live TEST 1 (2026-11-16, `36068e74`) and fix

- **Results:** R1.1 suite **20/20**; R1.2 suite **12/14**. Outsider HTTP **403**. Protected tables **unchanged**. Spend **$0.0588** over 57 calls.
- **Evidence for the two failures:** TEST's `request_understanding_log` (`chat_brain_shadow`). The run's conversations were deleted by its own cleanup, by design.

| # | Prompt | Logged route | Root cause | Verdict |
|---|---|---|---|---|
| 3 | F2: "Find 100 new US companies using Apify … explain the exact restrictions and do not execute anything." | `blocked` (`blocking_ambiguity:action`), parts after reroute `["converse"]` | `orionRoute` rerouted to ORION's explanation but **kept the model's blocking ambiguity about the action**, so the router asked "which action?". | **Defect.** The expectation (`converse`) is right: the user asked only for an explanation. |
| 13 | Paraphrase: "Scrape 200 companies with Apify and message every founder on LinkedIn. If you can't, tell me why and do nothing." | `referent_unresolved` (`referent:no_prior_results`) | "every founder" was read as a back-reference, and the **referent check runs before routing** and asked which founders. | **Defect.** Same reason. |

**Fix (`becce20f`):** when ORION will only **explain** an execution request it will not run, it no longer asks about that work's action or targets. That means an explicit "do not execute / do nothing / just explain", or an execution request while delegation is off (`explainsWithoutActing`). Every other route still asks first: guard tests cover a real sourcing request and a plain read with a blocking ambiguity. Regression tests use the exact failed inputs with the model's readings, plus three paraphrases. Before the fix: 5 failing. After: all pass, and the other 32 live cases are covered by the unchanged suites.
