# Mission compiler: open production-readiness issues

These issues were recorded during the independent reviews of PR #194 (A7 real-GPT interpretation fixes). They are **OPEN**: none is resolved by PR #194, and none may be closed without its own change, tests and review. The agency-only A7 TEST names a single role, so none of them affects that test's interpretation gate. They do affect production missions that name several roles, or roles in other words.

| ID | Issue | Current behaviour | Why it matters | Status |
|---|---|---|---|---|
| MC-1 | **AND role lists are recorded, not enforced** | "hiring AEs **and** SDRs" compiles to `role_terms ["account executives","sdrs"]` with `qualifier.role_match: "all"`. The job filter (`jobProvesRequestedHiring`) is per posting and any-of, and nothing checks that a company hires *every* listed role | A company hiring only AEs can satisfy a request for AEs *and* SDRs, so the request is broadened | OPEN |
| MC-2 | **OR / comma lists default to any-of** | A list joined only by commas, or by both "and" and "or", is read as alternatives (`role_match: "any"`) | Ambiguous lists are resolved toward the broader reading | OPEN |
| MC-3 | **Role authorization is lexical** | A model role term is kept only if the user's sentence contains it (a regular plural allowed). A synonym ("sellers" for "account executives") or a role the user wrote differently is removed and recorded (`hiring_role_not_in_request`). The role family stays only if the sentence or a kept term names it | Never adds a role, but can leave a hiring requirement family-only, broader than the model's restatement. Synonym and abbreviation handling ("AE" vs "Account Executive") rests on the alias table and isn't verified exhaustively | OPEN |
| MC-4 | **Role matching is lexical** | Titles are matched by whole words, plus regular plurals (`-s`, `-ives`, `-ers`, `-ors`, …, sdrs/bdrs/aes). Irregular plurals, abbreviations and title variants are not normalised | A genuine posting can fail to prove the hiring (narrowing), or a word match can be accepted without context | OPEN |
| MC-5 | **Negations are read only in one form** | `excluded_role_terms` is set only when a negation ("not", "except", "excluding", "other than", …) **follows** the hiring clause and names a role in the alias table or family reader. Other negations ("except for interns", negation before the verb) are not read as exclusions | A stated exclusion of an unlisted role isn't enforced | OPEN |
| MC-6 | **A contradictory exclusion is refused only by the TEST gate** | "require AE, exclude AE" is kept on the mission and recorded (`hiring_role_excluded_and_required`), and the real-GPT interpretation gate (I9) refuses it. Production compiles have no such gate: the mission fails closed at runtime (no posting can prove it), spending effort without results | Needs a production-side refusal or clarification step | OPEN |
| MC-7 | **A model window that differs from the user's is not reconciled** | If the proposal states a window other than the user's ("within 30 days"), the compiler carries the model's value. I5 catches it in the TEST gate | Production compiles can silently use the wrong window | OPEN (predates PR #194) |
