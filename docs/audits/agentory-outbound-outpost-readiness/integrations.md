## Verified external feasibility, with limits

Apollo documents saved-contact search separately from prospect database search. Approved record retrieval is feasible in principle; it is not proof of Agentory support or Nosh's access. [Contacts search](https://docs.apollo.io/reference/search-for-contacts).

Apollo exposes update-by-contact-ID and typed custom fields. Lists can be replaced when updating labels, so the proposed adapter must approve exact fields and preserve unrelated state. Do not create another contact when an existing ID is known. [Update contact](https://docs.apollo.io/reference/update-a-contact), [create/deduplication behavior](https://docs.apollo.io/reference/create-a-contact).

Apollo rate limits vary by endpoint and plan, apply at team level and use multiple windows. Resolve actual limits before choosing polling cadence; persist cursors and respect Retry-After. No numerical Nosh account quota is assumed. [Rate limits](https://docs.apollo.io/reference/rate-limits).

LinkedIn's current SNAP overview states that new partner onboarding is not being accepted. Approved partner permissions are required. An Agentory integration cannot be promised from a Sales Navigator seat alone. [Official SNAP overview](https://learn.microsoft.com/en-us/linkedin/sales/).

The candidate iGTM page describes custom CRM field/context/outcome integrations but supplies no validated account-specific webhook contract for this audit. Its stated implementation timing is marketing, not an Agentory estimate. [Vendor integrations page](https://igtm.ai/integrations). Direct retrieval timed out; indexed official text was available. Confirm the vendor and obtain the contract.

Candidate Jungler documentation describes an API key and workspace scope, and lists webhook/Sheets/Slack output routes. The quick-start body was not retrievable through the page opener; indexed official documentation supports conditional API feasibility only. [Jungler documentation](https://docs.jungler.ai/), [quick start](https://docs.jungler.ai/docs/quick-start/). No numeric limits or webhook delivery guarantee is asserted.

Sheets' official limits document project/user quotas and bounded exponential backoff. Slack documents event delivery and retries; neither service supplies exactly-once end-to-end business processing for this proposed integration. [Sheets limits](https://developers.google.com/workspace/sheets/api/limits), [Slack Events API](https://docs.slack.dev/apis/events-api/).

## Proposed connection contract — not implemented

Reuse Agentory as a processing layer around the existing CRM. Persist `workspace/client binding`, source system and immutable external record ID on every imported record; retain source facts and timestamps rather than overwrite them with model summaries. A model proposes a patch; a deterministic validator and human authorize the allowlisted write. Separate ingestion, research, decision, approval and delivery states so a successful draft cannot mean a successful CRM update.

Inbound event identity must include vendor account and client/campaign. Persist raw signed event metadata safely, deduplicate before effects, order by a vendor sequence/version when available, and quarantine ambiguous contact matches. A delayed “not interested” must not overwrite a newer “do not contact,” and opt-out must dominate outbound scheduling. These rules cannot yet be tested through an iGTM adapter because that adapter does not exist.

Deliver through a durable outbox with explicit intended/pending/accepted/uncertain/reconciled states and remote operation IDs. A timeout is not proof of failure. Reconciliation reads the destination before replaying an uncertain operation. Vendor idempotency support and expiration must be confirmed; do not claim exactly-once delivery from a database lock alone. Start read-only, then approved writes to a sandbox with a separate explicit authorization.
